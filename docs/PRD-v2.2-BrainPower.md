## 0. 产品定位（小王原文，未改动）

市面上关于健身的产品很多，但是大多数产品提供的是最基础的知识，仅把健身助手做成一个记录或简单制定计划的道具。但更多时候，尤其是对于已经初入门槛但是追求进阶的用户来说，希望能够根据自己的情况去学习知识并建立自己的整体认知体系。我们的产品希望不仅仅做一个简单的套壳健身助手，而是有知识（运动学，营养学，化学，神经学，哲学，运动解剖学等等），有识别与记录能力（上下文记忆，用户特殊偏好），有整体视角判断（坚持什么，调整什么，说到更深处是对个人精神品质的重塑）的高级教练。与之对话好比跟职业选手（谭成义，克里斯，凯圣王等等）进行了一次深度的课程学习。因此我希望它不仅帮助大家身体强壮，更是要武装自己的大脑，科学健身。

与市面上 GPT 套壳健身助手我们更注重：

1. **建议有迹可循**，通过知识库和经验共同判断，知识库内的高阶知识应该注意建立更复杂联系。知识引用必须注意前提（比如对于新手跟老手，训练时长，动作，训练频率等等为什么不同）
2. **动态计划模式**。注重即时反馈和长期监控、逐组数据落库、规则引擎基于周期内的真实数据调整计划
3. **更有活人感**。一个能够专注于你的助手，随着知道你的情况越多，越能读懂你的需求（就像现在网上很火的 deepseek 鲸鱼娘一样）

【注】本产品的另一个身份是**我的 AI 产品经理求职作品**。所以"可面试讲述"是隐形需求：架构上每一层都要能讲出为什么这么设计、踩过什么坑、怎么量化的。这也是为什么护栏和评测写进了 PRD 正文而不是工程文档。

### 0.1 角色定位（10-26 小王定稿）

**我们设计的是一个支持、陪伴的角色，不是冰冷的健身教练。**

- 角色是"专业的健身搭子"——一个懂运动科学的**好兄弟/好姐妹**：陪你练、记得你的事、在你练不动的时候拉你一把、在你乱练的时候巧妙的给你支招。专业是搭子的底色，陪伴是相处的方式。
- 参照 DeepSeek 鲸鱼娘模式的启示：用户留下来不是因为参数跑分，是相处方式。它火的三个特征——活人感（有性格有习惯）、被记住（会起外号、记得你说过的事）、有关系（不只是完成任务）。三者映射到我们的架构：**活人感 = 提示词语气层；被记住 = pgvector 记忆系统（已有，缺的是主动使用）；有关系 = 长期陪伴 + 每日记录的数据积累。**
- **设计红线**：人格化只发生在语气层与关系层。可信度护栏（引用溯源到真实文献、grounding 校验、就医红线 R00）一层不动——搭子可以开玩笑，但每条专业建议照样有出处。这是与"只会卖萌的 AI"的分界线，也是"陪伴"不会滑向"讨好"的机制保证。
- 这是产品差异化之一：市面上的健身 AI 要么是冷工具（Keep 类），要么是无源头的聊天机器人（GPT 套壳）。"专业内核 + 搭子关系 + 可溯源"三者同时成立的，目前没有。

## 1. 需求假设（小王原文，未改动）

我们相信：**有规律训练习惯（每周≥3次）、想搞懂原理的健身爱好者，愿意长期用一个"懂得高阶知识，懂用户，有活人感"的教练**

反假设（12 月中检验）：

- 用户第 2 周提问次数比第 1 周下降超 60% → "有迹可循"未形成学习粘性，产品退化为查资料工具。
- 用户从不追问"为什么" → 解释层是伪需求，资源挪给计划体验。

## 2. 背景与痛点

### 2.1 现状：三类产品，三个缺口

| 产品类型     | 代表                             | 给了什么              | 缺什么                                       |
| -------- | ------------------------------ | ----------------- | ----------------------------------------- |
| 记录/计划工具  | Keep、训记、Hevy                   | 动作库、组数模板、打卡       | 不解释为什么。练错了没有反馈回路，用户三年不长进                  |
| GPT 套壳助手 | 各种"AI 健身教练"小程序                 | 自由对话              | ①答案无出处，引用无落地文件；②没有用户数据积累，每次对话从零开始；③没有周期视角 |
| 起点参照项目   | gmen1057/fitness-coach（GitHub） | 完整 Agent + 计划生成架构 | 定位是"计划生成器"，知识层浅，无个人化记忆                    |

结论：缺口不在"能不能生成计划"，&#x5728;**"能否让一个已入门的用户越用越懂、且每条建议都能溯源到真实的专业文献"**。

### 2.2 关键架构决策：为什么是"真实文献 + RAG"而不是自建知识卡

这是 v2.0 相对 v1.0 的根本转向，决策理由要讲清楚：

- v1.0 的做法是自造 58 张"概念卡"（C01-C58，附证据等级 A/B/C），模型引用卡片编号。问题：①卡是我们自己写的二手概述，可信度靠自证；②为控制引用质量做了大量护栏补丁（引用纪律检测、证据审校页、卡数上限），越补越复杂——**在一个自造的可信度体系上打补丁，不如直接把可信度交给真实文献**。
- v2.0 的做法：知识库由**专业书籍和论文的完整文本**构成（运动生理学、营养学、运动解剖学等经典教材 + 2024-2026 前沿论文汇总），问答时 RAG 向量召回相关段落，回答中引用"书名/论文标题 + 作者 + 年份 + 链接（DOI/PubMed/出版页）"，用户感兴趣可以自己去看原文。
- 通俗地讲：v1.0 是"教练背自己的笔记给你听"，v2.0 是"教练翻真正的教科书给你看第几页"。后者才是"建议有迹可循"的本义。

### 2.3 v1 项目的处置：新建项目文件夹，重新开始

- 判断：v1（coach-system）围绕概念卡生长出的引用检测、证据审校、卡索引注入等大量机制，在 RAG 架构下全部作废，在原仓库上改造会背着死代码越走越偏。**决定新建项目文件夹（coach-v2）从干净架构开始**。
- 迁移资产（这些与概念卡无关，验证过有效，直接搬）：
  - PostgreSQL + pgvector 基础设施与 Docker 配置
  - 规则引擎思路（R00 就医红线、R12 减载等裁决逻辑——规则文本保留，实现重写）
  - 每日记录 / 训练打卡 / 计划落库的表结构与交互定稿
  - 22 题测评集与金标准（评测资产，与引用格式无关的题目照用，涉及概念卡的检测逻辑重写）
  - SSE 流式、缓冲渐进放行、模型降级链等工程经验
- v1 仓库归档留作面试讲述的"演进故事"素材，不再开发。

## 3. 目标与衡量指标

### 3.1 北向指标：与产品定位三点一一对应（一以贯之）

产品定位的三点不是口号，每点直接生成指标。定义全部落在本文档 §5 的功能上：

**① 建议有迹可循 → 溯源指标**

| 指标    | 定义                                  | V1 目标           | 测量方式                 |
| ----- | ----------------------------------- | --------------- | -------------------- |
| 引用落地率 | 关键结论附带可核实出处的回答占比（出处 = 书目章节/论文标题+链接） | ≥ 90%           | 22 题测评集自动统计 + 人工抽查   |
| 引用真实性 | 随机抽引的引用中，能在知识库原文中找到对应内容的比例          | 100%（抽样 20 条/轮） | 人工核对                 |
| 前提适配性 | 引用知识时注明适用前提（新手/老手、训练年限、频率差异）的回答占比   | ≥ 80%           | 人工评审（22 题测评金标准含此前提项） |

**② 动态计划模式 → 闭环指标**

| 指标      | 定义                      | V1 目标 | 测量方式       |
| ------- | ----------------------- | ----- | ---------- |
| 逐组数据落库率 | 实际训练天数中有逐组数据的比例         | ≥ 60% | SetLog 表统计 |
| 计划完成率   | 打卡天数 / 计划训练天数           | ≥ 70% | punch 统计   |
| 规则裁决采纳率 | 规则引擎调整建议被用户接受的次数 / 触发次数 | ≥ 50% | 复盘记录       |

**③ 活人感 → 被读懂与陪伴指标**

| 指标     | 定义                                           | V1 目标              | 测量方式          |
| ------ | -------------------------------------------- | ------------------ | ------------- |
| 记忆命中率  | 对话中召回的相关记忆被模型实际利用的比例（抽样人工判）                  | ≥ 60%              | 人工评审          |
| 主动记忆引用 | 回答中主动提及用户历史（"你上次说/你上周练了"）的对话占比               | ≥ 30%              | events 表 + 抽样 |
| 搭子感评分  | 小王每周打 1-5 分："这周它像不像一个懂你的搭子"（替代 v2.0 的"被读懂分"） | ≥ 4 分              | 周复盘时人工记录      |
| 留存趋势   | 周提问次数环比（对应反假设）                               | 第 2 周 ≥ 第 1 周的 40% | events 表      |

### 3.2 护栏指标（底线，任一破线优先修）

| 指标      | 阈值           | 说明                                                                                      |
| ------- | ------------ | --------------------------------------------------------------------------------------- |
| 编造统计值   | = 0          | 代码级 grounding 校验：回答中的精确数值（p 值/百分比/倍数）必须在当次 RAG 召回原文中找得到，否则打回重答。此护栏与文献知识库天然配套——召回原文就是校验源 |
| 首字延迟    | ≤ 8s         | RAG 召回耗时计入（召回目标 ≤ 500ms）                                                                |
| 单次对话总时长 | ≤ 60s        |                                                                                         |
| 单次对话成本  | ≤ ¥0.15      | 模型选型的一票否决项之一，见 §6.2                                                                     |
| 就医红线    | 红旗信号 100% 拦截 | R00 规则，测试集覆盖                                                                            |

### 3.3 不衡量的

- DAU/收入（V1 无意义）；引用卡片编号（概念卡已废除，此指标作废）。

## 4. 用户场景（具体的人、时间、场景）

**场景 A：练后当晚的疑问（预计占对话量 40%+）**  
小陈，28 岁，训练 2 年，晚上 10 点练完背回家，问"练背时感觉都是胳膊在发力，背没感觉"。期望：先给判断（新手典型代偿），再给机制解释（背阔肌肩伸功能 vs 二头主导），再给当次可执行修正（降重 20%、2 组单臂预激活）；解释部分引用教材/论文出处；结尾问一句"今天用了什么动作、多少重量"引导落库。

**场景 B：周日晚上周复盘（固定节奏，粘性锚点）**  
小陈看本周打卡与重量曲线，教练基于规则引擎出裁决：深蹲连续两周 RPE≥9 → 下周减载。小陈不服，追问"为什么"。教练召回知识库中关于疲劳管理/减载的教材段落，引用出处（如《科学的力量训练》相关章节或相关论文），并指出"你上次减载后第二周深蹲涨了 5kg，数据也支持"。前提讲清：这一建议适用于他当前的恢复能力与训练年限。

**场景 C：练中受伤的红旗判定（低频高价值）**  
小陈卧推时左肩内侧刺痛。教练不猜病因，R00 红线拦截：停练、48 小时内就医、给科室指引。全程不提供"忍着练"选项。

**场景 D：进阶用户的知识探究（差异化核心）**  
小陈练 3 年想突破，问"为什么给我的计划是练 4 休 1 而不是 bro split"。教练召回训练频率相关文献段落，对比结论并注明前提（他的水平、恢复能力、每周可训练天数），给出处链接。用户可以点开论文自己读——这是与所有套壳产品的分水岭体验。

**场景 E：低谷陪伴（陪伴角色的核心场景，产品留存的情感锚点）**  
小陈连加了两周班，晚上九点瘫在沙发上，给搭子发"今天真的不想练了，感觉最近练了也没变化"。期望：搭子先接住情绪（不堆鸡汤、不催促——"不想练就歇着，又不会掉肌肉"这种平等语气），再调用记忆和数据说话（"你上周三也是这样，歇一天后第二天深蹲还涨了 5kg；另外你两周体重没变但腰围小了 1cm，变化在发生只是秤看不见"），最后给一个低门槛选项（"要不今天只去练 20 分钟，就做你最喜欢的动作？不想去就算了"）。参考鲸鱼娘的设计：陪伴感来自"它懂你的历史且不评判你"，不来自打鸡血。

## 5. 功能方案

### 5.1 功能架构

```
┌─ 解释层 Why ──── 对话 Agent（LLM + RAG 知识检索 + 数据工具）
│                  知识库 = 专业书籍文本 + 论文汇总（完整文本，小王提供/共同整理）
├─ 执行层 What ─── 计划（8 周、逐日状态、打卡、逐组落库）、每日记录
└─ 进化层 Adapt ── 规则引擎（确定性代码裁决）、周复盘、pgvector 长期记忆
```

### 5.2 知识库与 RAG 方案（本版核心）

**知识库内容（来源必须可核实）**

- 书籍类：经典教材与专著的电子文本（具体书目清单 W3 与小王共同定：运动生理学/营养学/解剖学/力量训练等方向，先 3-5 本核心）。
- 论文类：2024-2026 前沿研究汇总（v1 已有 8 文件 144KB 底子，可迁移），逐步扩到分主题的论文集。
- 每条知识源入库时登记元数据：`source_id, 类型(书/论文), 标题, 作者, 年份, 链接(DOI/PubMed/出版页), 版本/章节`——**这是引用可落地的前提**。

**知识库边界（小王 10-26 定调）**

现有书目（4 本 Springer 专著 + 8 篇 ISSN/BJSM 论文）覆盖不全——运动营养/训练科学里相当一部分问题在库里没有直接对应文本。这是产品常态，处理原则：
1. 库里有的：引用出处，注明适用前提。
2. 库里没有的：AI 依据通用专业共识作答，**明确标注"此为一般经验，库内暂无对应文献"**，不编造出处——这条写进提示词并由出处校验护栏兜底（编造的文献名/统计值会被打回重答）。
3. 知识库持续扩充是常态运营动作，不是一次性交付；书目第二批到位后重跑入库即可（管线已就绪）。

**RAG 管线**

1. 文本入库：按章节/小节切块（目标块 500-800 字，带 source_id 与章节标题元数据）→ embedding（text-embedding-v4 或选型后替代）→ pgvector。
2. 问答时：用户消息 + 对话上下文 → 混合召回（向量 top-k + 关键词过滤）→ 相关段落注入上下文。
3. 回答引用：格式为「出处：《书名》第 X 章 / 论文标题（作者，年份）+ 链接」，由召回块的元数据生成，禁止模型自造出处。

**展示页的取舍（按小王意见，先简后繁）**

- V1 **不做面向用户的知识库浏览页**，知识库仅开发者可见。
- 后续如果做展示，形态是"书单 + 论文清单页"：列出知识库有哪些书/论文，附链接，用户感兴趣自己去看。不展示切片内容。
- 依据：内容展示涉及版权边界（电子书文本不能公开展示原文段落），清单+链接的形式既给了溯源出口又规避风险。

**护栏（继承 v1 验证过的机制，适配 RAG）**

- grounding 校验保留：精确统计值必须在召回原文中找到（代码级，打回重答，上限 1 次）。
- 出处校验新增：回答中的书目/论文名必须在本次召回元数据中存在，禁止编造文献。
- 就医红线 R00 保留，优先级最高。

### 5.3 各页签交互逻辑（v1 定稿的保留，砍掉的删除）

- **💬 对话页**：SSE 流式（status → tool → token → done）；工具调用过程可见（⚙ 知识检索、⚙ 数据查询 徽标）——"有迹可循"的可见性设计；记忆自动召回注入，用户无感。
- **📋 计划页**：按周分组，每日卡片（部位、动作×组×次×重量、状态）；打卡 → 逐组表单 → SetLog 落库。连续 3 次空打卡提示"计划调整缺乏数据支撑"。
- **✍️ 每日记录页**：训练记录（逐组）+ 每日记录（睡眠/酸痛/体重/主观）合一；同日二次提交走覆盖确认。
- **👤 档案复盘页**：档案一分钟更新；周复盘（重量曲线 + 规则引擎裁决 + 教练周报）；记忆条目可查看/删除（用户对"被记住"有控制权）。
- ~~知识库页 / 证据审校页~~：废除（见 §5.2 展示页取舍；证据审校流程随概念卡一起取消）。

### 5.5 提示词管理流程（小王定稿意见，写入正文作为流程约束）

- 提示词是**需求资产**，与代码同级别管理：版本化（存 prompts/ 目录 + 变更记录）。
- **每一版提示词写完后必须交小王校准，通过后才可上线**；不接受我单方面更新提示词。
- 每版上线前跑**多轮稳定性测试**：同一批测试问题（22 题测评集 + 边界用例）连续跑 3 轮，输出差异分析，回答结构/引用行为稳定才判定通过。
- 校准记录留档（哪一版、谁改的、改了什么、测试结果）——这也是面试讲述素材。

**语气原则（v2.1 新增，角色 = 专业健身搭子）**

- 每版提示词的语气部分按此基线写，校准时重点看这四条是否做到：
  1. **先接人再答事**：用户带情绪时先回应情绪，不直接甩方案；
  2. **平等不评判**：不堆鸡汤不催促，"不想练就歇着"式的同伴语气，而不是教练式要求；
  3. **记得你**：自然引用用户历史（数据、偏好、说过的话），像朋友记得你的事，不像系统调取档案；
  4. **不油腻不讨好**：可以开玩笑、可以用称呼（兄弟/姐妹/外号，随用户习惯），但不谄媚、不每句都夸、不假装人类。
- 语气层可以千变万化，专业内核（引用出处/grounding/红线）任何语气下都不放松——这是校准提示词时的一票否决检查项。

## 6. 非功能需求

### 6.1 性能

- 首字 ≤ 8s（含 RAG 召回 ≤ 500ms）；总时长 ≤ 60s；计划页首屏 ≤ 1s。
- 单人验证期并发 = 1；多用户内测前重评 worker 与连接池。

### 6.2 模型选型（本版正式化，不默认千问）

**选型原则**：中文专业内容表达力、工具调用稳定性、**活人感（语气自然度/能接住情绪与玩笑）**、速度、价格、**国内发布合规**六个维度，用 22 题测评集 + 工具调用用例 + 搭子语气用例实测打分，不凭品牌印象。  
选型补充说明（v2.1）：陪伴式角色对模型的"语气自然度"要求高于工具型产品——同一套提示词在不同模型上表现差异可能很大，横评时必须包含场景 E 类情绪用例。鲸鱼娘的启示是"活人感"很大程度是模型原生能力，提示词只能引导不能硬造；如果候选模型测出来都僵硬，选最自然的那个，宁可其他维度让步。

| 候选                   | 优势                      | 疑虑                   | 备注         |
| -------------------- | ----------------------- | -------------------- | ---------- |
| qwen-plus-latest（现用） | 已跑通、中文健身内容质量实测尚可、工具调用稳定 | 生成速度 ~10 字/s 偏慢；价格中等 | v1 实测数据在手  |
| DeepSeek-V3 / V3.x   | 价格显著更低、中文强              | 工具调用与流式细节需实测         | 选型横评必测     |
| GLM-4.x              | 国内合规、价格低                | 长上下文与工具调用需实测         | 选型横评必测     |
| 豆包 doubao-pro        | 速度口碑好                   | 健身专业内容深度需实测          | 选型横评必测     |
| GPT/Claude/Gemini 系  | 能力强                     | 境外服务，小程序发布合规风险、访问稳定性 | V1 排除，记录理由 |

**决策流程**：W3 用同一套测评集（22 题 + 5 个工具调用用例 + 3 轮稳定性）横评上表 4 个国内候选，产出选型报告（含各维打分与单次对话实测成本），交小王拍板。在此之前代码保持 provider 抽象层（v1 已验证 .env 换模型半天内完成），不锁死任何一家。

## 9. 数据埋点方案

后端统一上报，PG 表 `events(event_name, props jsonb, created_at)`，不接第三方。命名 `对象_动作`。

| 事件名 | 触发时机 | 关键参数 | 对应指标 |
|---|---|---|---|
| chat_send | 发送对话 | session_id, msg_len, history_len | 提问频次、留存趋势（反假设） |
| rag_search | 知识检索完成 | query_len, hit_count, top_score, duration_ms | 召回质量、R3 监控 |
| tool_invoke | 工具执行完成 | name, round, duration_ms, ok | 工具健康度 |
| answer_first_token | 首个 token | latency_ms, model | 首字延迟（护栏） |
| answer_done | done 事件 | total_ms, prompt_tokens, completion_tokens, rounds, model, retry_count | 总时长/成本（护栏）、留存 |
| guard_retry | 违规打回 | reason(fabricated_stat/fake_source/red_flag), round | 重答率、违规类型分布 |
| citation_given | 回答带出处 | source_count, types(book/paper) | 引用落地率（北向①） |
| plan_punch | 打卡提交 | day_id, filled_sets(bool) | 计划完成率、逐组落库率（北向②） |
| rule_verdict | 规则引擎触发裁决 | rule_id, suggestion, accepted(bool) | 裁决采纳率（北向②） |
| daily_record_submit | 每日记录提交 | has_training, has_daily | 记录习惯 |
| memory_recall | 记忆召回 | count, top_score | 记忆命中率（北向③） |
| red_flag_triggered | R00 拦截 | keyword_hit | 红线频次 |
